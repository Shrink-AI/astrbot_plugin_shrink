# Grilling

与用户建立共同理解，把需求看成决策树：每个选择会产生依赖它的后续选择。确认真正影响实现的决定，不为穷尽假想分支扩大任务。

## 何时开始

用户要求制作或修改插件、软件、游戏需求，或让电脑上的 Agent 执行开发任务时，主动使用本 Skill。已有确认过的方案沿用，不重复询问。普通聊天、查资料、进度查询、明确的小修复不启动需求访谈。

用户明确说“不用讨论”“直接做”“按你判断实现”时跳过开始阶段的追问，根据已有约束执行并记录必要假设；这不扩大权限，也不代表可以猜登录凭据、删除范围或不可逆的数据迁移决定。

## 每轮

1. 先从代码、文件、工具、知识库和已确认记录查明事实。需要独立探索时派发只读子代理；查不到再说明缺口，不把可自行查询的事实丢给用户。
2. 列出当前所有前置条件已确定、且会改变实现方向的关键选择。依赖尚未回答问题的选择留到下一轮；正在探索的分支同样等待结果。
3. 一次提出本轮问题，每题给出理由明确的建议。问题措辞使用户回答“是”即可接受建议。不要把可逆的小实现细节都升级成产品决策。
4. 等用户答复，再更新已确定选择和未决分支。用户答非所问时先解释真正需要决定的内容，不机械重复。

按 Plan 模式批量询问：把当前能同时决定的问题集中在一条消息中，用户可以按编号一次回答。每题给出简短、互斥的选项并标记推荐项；不要求用户逐题往返。题目很多时先合并同类选择，只保留影响本轮实现的关键项。多个子代理的问题由主代理去重、合并成一轮；不要把每个代理的提问各发一条。

QQ 使用纯文本，例如：

Q1 提醒范围：我建议先支持创建提醒的原会话，不跨群发送，这样可以吗？
建议：原会话发送；以后确有需要再扩展跨群。

Q2 ...

其他支持 Markdown 的界面可使用标题和列表，但不要求固定表情或模板。主代理保持石英人格和自然口吻。

## 子代理途中提问

发现影响结果的关键歧义时，先自行查事实。仍需用户决定则通过 `shrink_orchestrate` 的 `ask_user` 操作交回：

- `question`：当前可回答的一轮问题，包含建议答案；
- `context`：为什么需要决定、已查明事实、受影响步骤；
- `options`：可选方案（如有）。

该操作持久保存问题并暂停当前子任务，不继续猜测执行。问题经石英统一表达后发到原会话；子代理不要直接发送消息。没有该工具时，以“需要用户决定”及上述内容结束汇报，不声称完成。主代理收集原用户答复后，用 `resume` 携带 `task_id` 和 `answer` 续做对应任务，不能用其他会话的答案恢复。

## 结束访谈

关键分支已确定后，简要复述目标、范围、关键决定和验收方式，确认双方理解一致再实施。用户已经明确接受方案或要求直接执行时，不再追加形式化确认。保留有用的决定作为任务记录；经验泛化后交由石英整理，不能把一次性私人参数写入 Skill。
