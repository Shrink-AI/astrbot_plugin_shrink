# 石英核心与 AstrBot 集成

## 职责与数据所有权

- `Application` 组合领域服务和本地仓储，不依赖 AstrBot 的生命周期或 HTTP 管理接口。
- `services` 负责聊天判断、资料整理、记忆校验、经验复盘及草稿管理。资料原文不是指令，接入工具的返回值也不能直接写成长期记忆。
- `persistence` 保存人物、来源、确认、版本、撤销、聊天和操作证据。知识库正文的本地字段是兼容投影及待同步编辑，不是第二份独立正文。
- `adapters` 负责 AstrBot 的知识库、原生 Skills、子代理、定时任务及管理接口。`PluginHost` 负责这些适配器的启动与关闭。
- `api` 和工具入口只负责权限、参数转换、调用及结果展示，复用同一业务服务。
- CraftTable、Gitea、bothouse 接入插件只提供项目工具。石英决定是否整理其结果，核心统一保存来源与记忆。

## 依赖方向

```text
main.py → PluginHost（装配与生命周期）
                 ├─ AstrBot 适配器 → services / persistence / ports
                 ├─ HTTP API      → 应用服务接口
                 └─ Application   → services → persistence / ports / prompts
其他插件 → AstrBot 工具注册表 ← 石英发现并调用
```

`services`、`persistence` 和 `api` 不导入 AstrBot 或 `adapters`。宿主事件、插件加载、原生知识库与管理 API 均由适配层处理。`Application` 的宿主能力由 `PluginHost` 装配；HTTP 路由调用已装配接口，不构造 AstrBot 事件。任务上下文位于 `services/task_context.py`，聊天钩子和代理编排不通过相互导入传递任务身份。

工作台负责草稿、路径约束、差异、测试证据、冲突检查及备份恢复；宿主加载与源码读取通过 `AstrBotWorkbenchRuntime` 注入。独立部署执行器可以复制并导入工作台文件，不依赖正在卸载的核心包；使用说明通过回调注入。`Operations` 是现有开发与编排的兼容门面，`AgentTasks` 仍为其内部实现，不是供其他插件继承的公共 API。

草稿与线上冲突时，`refresh` 归档旧草稿、原基线和测试记录，再检出当前线上源码；不部署、不合并旧修改。`archives` 列出归档，`read_archive` 按归档 ID 和相对路径读取旧文件。新草稿必须重新测试，部署仍校验线上基线。提示词 TOML 文件参与检出、差异、隔离测试及版本校验。

## 决策层

规则、候选召回、可替换后端、结构与规则复核、路由由 `services/decisions.py` 统一处理；`persistence/decisions.py` 保存最近 14 天的决策依据和规则直达比例。Haiku 通过宿主 provider，Laya 通过可配置 HTTP 端点；默认只启用 Haiku，调用时限 3 秒。Laya 的实际接口未核实。决策不能授予权限或改变既有身份／会话／任务绑定，追加输入时再次复核；目标不明的停止只询问。

参与规则、跨会话追问、任务跟进及补充目标的替换／降级边界、工具候选、后台记录与离线 JSONL 协议见 [决策接口与离线评测](decision-layer.md)。候选最多 5 个不代表实际工具仅有 5 个，继续发现和前台长执行限制保留。主聊天仍使用宿主 agent 阶段和同会话锁；决策不会等待后台任务或增加外发消息入口。

## 可选插件边界

- 核心不导入其他插件模块，不要求接入插件安装，也不按其他插件名称拒绝启动。多个插件同时响应聊天时，由 AstrBot 会话启用范围和部署配置管理，核心不替其他插件启停。
- 外部能力只通过 AstrBot 已启用工具发现与调用；插件移除后，工具发现结果变化，核心聊天和资料整理继续可用。缺失工具是该任务的明确阻碍，不能伪造替代结果。
- 核心只修改 `handler_module_path` 属于自身模块的工具描述及参数说明，即使其他插件注册同名工具也不修改其定义。跨插件重名仍应由注册方解决。
- 项目、空间、账号、凭据和站点调用规则归接入插件。核心不解析专属工具名或中文回执，不在领域服务中添加站点分支。历史 `shirnk_plugin_workbench` 名称保留兼容，所有权属于核心。
- 专用运维探针可导入目标接入插件，但必须置于 `tools/`，不能成为核心启动或测试依赖。常规测试不要求安装任何接入插件。

接入插件由各自仓库维护，独立部署、配置和启停，不随核心发布。按 [插件通信协议](plugin-protocol.md) 发布能力，按能力名和版本发现；核心仅提供人格表达与通用发现调用，不持有提醒等插件的业务状态或路由。接入插件不得读取另一插件的配置、访问其 host 或导入 data.plugins 模块。

## 工具结果约定

图片随原消息进入持续历史。`conversation_events.content_parts` 保存有序文字和
`attachment:<id>` 引用；`chat_attachments.position` 保留组件位置，旧记录按创建时间和
ID 迁移。原图归附件库，待保存的内联图片先写本地文件，数据库不保存图片 Base64。
已保存附件不重新下载；多个请求共用在途下载，请求构建最多等待五秒。

历史窗口先按每张图片 765 token 计算预算，再由 `adapters/chat_images.py` 在宿主请求边界
读取原图。窗口内不另设图片数量限制；图片和所属消息整体进入压缩，工具调用与结果保持配对。
压缩只接收文字、已有解读和图片引用，不发起视觉摘要调用。旧检查点通过原消息引用补出附件目录。

`shrink_chat_history` 保留关键词、人物和时间查询，并返回消息 ID、图片数量及保存状态。
传入 `message_id` 后直接读取该消息的 `image_index`（默认 0），通过原生 `ImageContent`
供下一轮模型使用，同时返回总数、下一张索引和稳定引用。查图不发送平台消息。
读取与请求恢复都校验完整会话身份、撤回和纠正状态；保存中、下载失败、文件缺失及非视觉配置
分别报告。已有自定义工具说明自动补充两个可选参数，不改写用户原说明。

派工只携带本轮、明确引用或已通过历史工具读取的图片。同构体检查点保存稳定引用，
每次模型请求前按原会话重新解析；重复图片也保留各自原消息身份。诊断只记录图片数量和状态，
不记录图片字节、签名地址或聊天正文。

普通工具结果继续按原样供模型理解。接入方可在 JSON 顶层增加可选的结构化证据，核心用它记录执行状态：

```json
{"result": "工具原有返回", "execution": {"version": 1, "status": "submitted", "task_id": "job-id"}}
```

`status` 支持 `submitted`、`running`、`completed`、`failed`、`unknown`；`task_id` 与 `receipt_id` 可选。核心只提取这些字段，不回显其他未知字段。该约定表示工具自己报告的事实，不是新的权限授予或真实性证明；单步完成不能等同整个任务完成，平台接受不能等同用户已读。

未声明版本、未知版本或纯文本回执不推断成功，超时只说明已调用工具而完成情况未确认。旧提示词键保留以兼容保存过的编辑与历史记录，但专属工具判断不再执行。接入插件可独立逐步采用协议，核心不强制它们升级，也不读取其私有数据库。

主人格的本轮工具答复就是最终表达，不因使用工具而再完整改写。`ExpressionService.finish` 始终清理推理／元叙述，复用 `outbound_guard` 检查外露并核对执行证据。只有外露或无证据执行声明才进入一次恢复表达；恢复仍失败时非必要内容静默，必要结果只使用已知状态的简短说明。该失败路径不回退草稿、facts、事件正文或异常全文。

普通聊天形态超过 `max(FORM_LIMIT[form] * 2, 60)` 或与近期回复重复时，使用原来的专用 `rewrite`，失败保留安全原文，再按整句取不超过 60 字符的内容；没有可用整句时在前 60 字符内最后一个分句边界（，、；：或空白）截取，完全没有边界才硬截。`tool_result`／`detail` 不查近期重复，超过 8000 字符直接截取，不因长度或重复静默。缩短改写的结果也不能携带外露内容或无证据声明。

用户明确要代码、配置、日志、工具查到的内容（`allows_tool_quotes`）或形态为 `detail` 时，前台允许必要的 JSON 片段与工具原文引用，代码块内不检查结构片段和提示词片段；整条裸 JSON、系统提示词原行及聊天模板标记仍拦截。`wants_detail` 仅决定回复形态；外露放行独立使用其超集，避免“你看这个方案怎么样”因此变成长回复。未明确要求时保持严格检查。前台只把执行／工具输出当作原始资料，不把聊天窗口、人物卡或表达示例拿来比对。后台 `safe_expression` 始终使用严格检查，不继承前台放宽参数。

无证据完成声明恢复使用 `kind=execution_status`，专用 `instruction` 要求只说明可确认的状态与缺少的回执，自然、简短、温和，不责备用户；没有记录不能推断未执行，也不能声称完成或承诺自动重试。这段要求不加入公共 `outbound.contract`。

早期源码与计划历史描述有两处区别：工具结果分支直接返回，不会继续经过普通短回复的长度／重复 rewrite；`Outbound` 是最多两次各 15 秒，并非每次 30 秒。无证据完成声明原来另走一次 compose，仍可累加占锁。当前安全恢复最多一次、预算 15 秒；普通缩短 `rewrite` 保留 30 秒，失败保留安全原文，安全恢复后不再叠加缩短模型调用。后台通知保留最多两次表达尝试。

前台与通知共用 `Outbound.persona`、`turn_context` 和 `outbound.contract`。前台提供本轮已按范围选取的资料及审计工具步骤；通知由可信 session／sender 解析同会话窗口和接收者，事实仍来自原通知及任务记录，不调用跨会话召回。资料字段不同体现各自业务范围，不把通知扩大成新授权。公共表达约定进入主模型稳定 system，开头限定只适用于工具／任务／执行结果，闲聊按人格与本轮要求来；其余只保留原 `outbound.compose` 的约定。发件箱模型同样使用它，通知继续经现有运输及发送回执。

2026-11-15 升级时将可识别的旧版六占位符 `outbound.compose` 全文覆盖拆为规则契约与资料壳。规则成为 `outbound.contract` 覆盖，对应定制段替换默认段，重复句去重，过时派工句由新契约取代；compose 恢复默认资料占位符。原全文仍在提示词历史，可在后台查看和恢复。`chat.persona` 覆盖逐字保留；目录外的旧键只保留历史，不参与加载，不恢复 acceptance policy 自动追加机制。按用户 2026-11-15 的决定，受理只说一句极简短句，不介绍同构体或派工过程，不加等待／回报尾巴；提到子代理时仍叫“我的同构体”。默认契约与线上人格覆盖的受理口径一致，无须编辑人格覆盖；结果、失败、未知与需要决定的事照常如实说明。

## 前台调度与共享资源盘点

2026-11-14 盘点，2026-11-15 审查返工更新。`services/scheduling.py` 统一拥有工作配额：聊天 8、管理交互 4（`interactive`）、规划 1、执行 3、普通后台表达 1、紧急表达 1、维护 1。模型、embedding、检索另按同名类别分配调用配额，工作槽和调用槽分开，避免持有工作槽后再次申请同一个信号量。父任务汇总使用规划槽，执行及持久重试沿用三路槽；本仓库没有额外的常驻 Planner 模型会话。普通聊天仍保留宿主同 UMO 锁，跨会话聊天使用聊天配额。

## 写入与恢复

记忆编辑经持久待处理队列同步至原生知识库，读回验证后才替换正文关联。更新失败保留旧知识库版本用于召回；删除和撤销先更新本地元数据，候选检索再按当前关联、状态和会话规则过滤。重排只能作用于已通过规则的候选。

经验保留原有复盘、版本和成败记录，发布为原生 `SKILL.md`。原生编辑回写经验版本，原生删除停用经验，双边修改冲突不能静默覆盖。原生路由标识使用 ASCII；中文标题、用途和步骤保留在文档中。

聊天原文独立记录。仅图片和表情包自动保存副本；普通文件、语音和视频不自动留档。资料整理保留用户明确交付的正文及来源，不自动抓取整个项目。

## 连续会话与输入收件箱

`input_events` 保存稳定输入身份（来源、会话、可信提交者、外部标识）、来源、原文引用及 received／claimed／processed 时间。正文只在 `messages`；消息、收件箱、角色日志写入同一事务。平台消息在防抖等待之前提交，去重早于任何模型或工具执行。其他插件命令处理器接管的消息及 /、!、！ 前缀命令不写正文，只在收件箱保留去重标识；不进入历史或检索。重复投递只设置 call_llm，保留其他插件的事件传播。不同发送者有不同输入及消费批次。停止与撤销授权绕过防抖，停止当前会话该创建者的任务；此入口不代替阶段 3 尚未实现的持续授权策略。

WebUI 写请求在鉴权及 CSRF 验证后入箱，客户端发送 `Idempotency-Key`，服务器回传 `X-Input-ID`。重复标识和相同内容返回持久结果；不同内容拒绝复用标识；中断后的已领取写操作结果未知时返回核对提示，不重跑写入。登录、登出及密码凭据不写原文库。附件正文仍由原上传接口保存，收件箱仅记上传操作。任务事件的稳定标识关联 `operation_events`；通知输入交给已有持久发送回执后完成消费，不把“输入已处理”解释为“消息已发送”。

原生定时输入以宿主 `cron_job.id + run_started_at` 标识一次运行，身份取宿主 payload 的创建者，不能把群号当成创建者。独立提醒持有业务、到期／周期计算和重试时间表，新投递通过 `message.notify submit/status/retry/cancel` 交核心发送；已经选择核心所有者后不能自行发送。兼容事件继续通过 `message.compose` 的 event_id 复用事件与表达，compose 保持 readonly；兼容发送者确认平台接受后调用 record_sent。

`task_inputs` 保存 input_id 到任务的绑定与 entered／processed 执行位置，不复制文本。原文来自收件箱引用，不能用模型传入的改写替换创建者原话。同一输入可绑定已有的多个任务，各任务只交付一次；所有绑定完成后输入整体 processed。entered 与执行检查点仍原子写入，取消和恢复沿用任务状态机。启动时平台收件箱仅重交未处理输入，使用宿主事件队列和原有回复路径，重新核对当前管理员身份；已处理输入不恢复。

`conversation_sessions` 保存实例、平台、群／私聊类型、平台会话 ID 和最近 system 前缀；`conversation_events` 是按到达顺序追加的 user／assistant／tool 日志。user 附带账号和展示名；工具调用保存参数和关联结果。到达工具执行期间的用户消息在原始日志中保留真实顺序，构造模型请求时放在完整 call/result 块之后，满足宿主提供者的工具消息配对要求。未闭合调用作为“结果未知，先核对”提示。前台发送观察器检查现有 event.send 的返回及原生发送标记；只有确认接受的正文进入 assistant 历史，草稿、发送异常及 False 回执不进入。统一通知的 record_sent 和附加气泡也写同一日志。

聊天仍走宿主 agent 阶段和同 UMO 串行锁。适配器设置 req.conversation=None，AstrBot 4.29.4 的历史保存入口会直接退出；req.contexts 从核心角色日志重建。删除原先清空 contexts 后仅靠文字群聊窗模拟历史、每轮向 system 添加记忆／Skills／动态表达材料、以及把多条原始输入改写为一条当前 prompt 的路径。人格、固定规则和管理员工具约定留在 system；本轮参考材料作为带数据边界的新 user 消息追加，最后是当前发言人的原话。

主聊天使用独立的 `history_compress_tokens`（默认 128000）与 `history_retain_ratio`（默认 0.65），`context_budget` 只管辅助窗口。角色／工具序列化文本按中文每字 0.6、emoji 每字 2、其余每字 0.3 估算 token；该值不是提供者精确计数，也不是整份请求的硬上限。达到阈值时，前台同步确定一次保留约阈值乘比例的最近原文边界，将覆盖范围及全部原文引用写入 `conversation_checkpoints`，立即返回，不调用或等待摘要模型，也不等后台锁。完整工具块和单条超大消息不拆开，孤立 tool 的窗口回溯不越过下标 0。

检查点统一保存 `window_budget`、`summary_tokens`、`summary_state`、`summary_attempts`、`summary_next_run` 和 `summary_claim`。没有摘要时正文为空，原文仍可取回；前台用同一查询路径读取固定边界，不因失败逐轮滑动。新检查点预留 `max(1, min(4000, int(阈值 × 0.2)))` 估算 token，默认阈值下为 4000；已有检查点沿用各自保存的预留值，无须迁移。前后采用同一预留值判定下一次越界；提示词用 `{{max_tokens}}` 传入扣除检查点引用说明后的摘要正文容量，生成后按同一估算容量截取作为兜底，避免摘要落地本身触发新边界。最近原文与固定 system 在两次边界变化间只追加；摘要落入原检查点时仅替换一次该前缀，落地后继续稳定。不承诺提供者缓存命中。

摘要任务归 `maintenance` 的工作及模型配额，单次模型调用 180 秒，最多共 3 次尝试，失败退避 2／4 秒；不占聊天名额。状态和尝试次数持久化，最终失败保留空摘要与引用，不由每个前台轮次重试。启动时将中断的 running 摘要按剩余预算转 pending 或 failed，后台补做原检查点，不重复建边界。完成写入须匹配领取标识；撤回／纠正删除检查点后，迟到结果不能复活旧摘要或覆盖新检查点。关闭应用会取消后台摘要，重启保留已消耗预算。

摘要请求的 system 与完整渲染材料合计上限按检查点换算：令 B 为其 `window_budget`，S 为其 `summary_tokens`，则 `L = max(32000, B + S + max(4000, ceil(B / 10)))`，单位为估算 token。检查点没有保存保留比例，因此以整个窗口 B 保守容纳一次正常覆盖范围，另加一份摘要 S 和至少 4000／窗口 10% 的模板、system 与序列化余量；32000 仅作小窗口的下限，不再是固定上限。计算只读取检查点的持久值，不使用后来修改的设置，不需迁移。

默认 B=128000、S=4000 时 L=144800；阈值上限 B=2000000、S=4000 时 L=2204000。默认保留比例 0.65 下，首次正常覆盖约 44800，后续约 40800 再加上一份摘要，均完整纳入。阈值调大时允许的摘要输入也会很大；这是估算容量，不保证所选提供者支持该上下文长度，须按模型实际能力选择窗口阈值。

优先使用最近可用摘要和其后到边界的原文；上一检查点失败时，失败范围仍包含在下一次材料内，直到触及该上限。只有累积失败范围、撤回后从头重建等明显超出正常覆盖量的材料才会按上限截取。超限只取靠近边界的最近完整消息／工具块，并在材料中注明前面还有未包含的更早记录。旧摘要若妨碍容纳最新完整块则省略；单块超过上限时也整块省略，不截断工具调用或结果。更早内容及省略块仍通过同一检查点的原文引用取回。撤回／纠正清空检查点后重新定边界时也执行这一上限，不把旧内容重新当作有效事实。

历史仓储幂等加列，为已有检查点补齐同一套字段：现有摘要为 ready，window_budget=0 表示尚未作为当前长窗口边界使用，不设旧数据专用过滤。旧 digests 检查点和原文引用仍可查，阈值内不遮掉角色历史。`history.compress` 使用双花括号，由真实默认模板测试验证。当前输入和本轮检索材料单独追加；`shrink_chat_history(keyword="checkpoint:ID")` 在原会话范围取回摘要对应原文，越界引用拒绝。

`services/context.py` 的 200 条扫描、120 字展示行、至少 6 条、20 分钟话题间隔及摘要截断仍用于记忆候选、表达参考和旧查询展示，不再决定主模型保留哪些聊天角色。跨群候选只经 RecentInteractions 选取，本轮追加，不写入 system，也不合并成当前用户的授权；任务跟进和外发表达维持同会话范围。

撤回和引用纠正追加状态，不改原文。OneBot 的 group_recall／friend_recall 通知按真实原消息标识关联；用户引用自己的原消息并以“更正／纠正／改为／改成”开头时追加替代状态。原记录仍能按引用检查，但当前上下文、近期窗口和涉及该记录的摘要不再将它作为有效事实；纠正与正在生成的摘要并发时，旧摘要不落检查点。

首次迁移前使用 SQLite backup（含 WAL）保存 `shrink.before-continuous-history-v1.db`；消息与摘要迁入同一日志／检查点结构，迁移版本只存在 kv，不给数据加旧数据标记。已有消息视为已消费，不在升级时重放整个历史。消息 ID 有实例信息时恢复所属会话；缺失实例的记录保留原来源，在来源能唯一关联实例时绑定，不能推断的多实例旧回复不复制给所有机器人。任务输入旧表同步转为引用结构，保留输入编号和执行位置。

`turn_traces.system_prefix_same` 为首次无比较值 NULL、相同 1、不同 0。它观察完整 system 前缀是否相同，不代表服务端提示缓存实际命中。

## 验收边界

语法正确、隔离测试通过、插件加载、真实功能运行和消息送达是不同状态。消息送达必须记录平台回执；发送结果未知时先查询记录，不能盲目重发。

接口、配置和模块边界允许破坏性变更。迁移保留来源、人物关联、确认状态与历史关系；修改前备份，升级后的调用方和后台必须使用新接口并完成实际验证。

## 任务状态、执行尝试和通知

任务 SQL、建表和备份在 `persistence/tasks.py`，转换规则与启动恢复在 `services/task_states.py`，调度和取消在 `services/task_execution.py`，执行与规划配额归 `services/scheduling.py`。`Operations`／`AgentTasks` 保留兼容入口及宿主事件、工具、runner 调用，不直接修改任务状态。运行期和迁移都经 `TaskStates.transition`，仓储使用前态比较更新；非法转换报错。任务状态改变与尝试结束／重试时间在同一事务提交。

三类状态分开存放：

| 结构 | 保存内容 |
| --- | --- |
| `operation_tasks` | 目标、创建者、原会话、依赖、业务状态、下一次执行时间、单步重试计数、执行／汇总阶段、停止请求 |
| `task_attempts` | 尝试 ID、执行器、宿主会话引用、检查点引用、开始／结束时间、尝试状态、结局、错误分类、重试序号及起始步骤 |
| `notification_receipts`、`task_delivery` | 真实发送回执和任务通知投影；HTTP 的 `delivery` 字段由关联查询返回，不再存入任务业务表 |

`session_ref` 保存宿主 UMO，`checkpoint_ref` 指向该任务的持久消息上下文。原生 runner 是进程内对象；人工恢复创建同一任务的新尝试，从检查点续做，不声称接管旧进程。操作事件关联尝试 ID；另一次尝试的工具结束不能抵消原尝试的未知写入。完成／确认取消后清理检查点，输入位置、执行记录、尝试和回执仍保留。

业务状态为 `queued`、`running`、`waiting_external`、`waiting_user`、`retry_wait`、`reconciling`、`needs_attention`、`completed`、`failed`、`cancelling`、`cancelled`。主路径见 agent-architecture-plan.md 7.4。实现补充以下调度边：排队任务可进入依赖等待或待处理；依赖／子任务返回后重新排队；外部回执可结束等待；原创建者明确续做可把待处理、失败、取消任务重新排队。已完成任务不能 resume。等待任务可停止；外部执行与核对中的停止也需经过 cancelling，不能假定远端已经停止。所有人工续做重新校验管理员身份、原会话、创建者、12 项上限及单开发任务限制。

### 旧状态映射与恢复

| 旧状态 | 迁移后的业务状态 | 处理依据 |
| --- | --- | --- |
| queued | queued | 无已开始且未结束的尝试即可重新排队；历史已结束尝试不阻止下一次排队 |
| running | 按恢复证据分到 queued／reconciling／needs_attention | 最新尝试未开始则 queued；工具开始未闭合则 reconciling；旧库没有尝试证据时不能假装仍在执行 |
| waiting | waiting_external | 保留等待；启动时若缺少尝试和外部等待依据，转 needs_attention，不盲目重跑 |
| awaiting_input | waiting_user | 保留问题，原用户答复后继续同一任务 |
| interrupted | needs_attention；存在未闭合工具时 reconciling | 不再把“进程结束”当成业务结局 |
| timed_out | needs_attention；存在未闭合工具时 reconciling | 旧库没有可靠单步重试预算，不凭超时文本自动重试 |
| blocked | needs_attention | 保留前置任务阻碍，不伪造已执行 |
| testing | needs_attention；存在未闭合工具时 reconciling | 没有结束证据不能假定测试仍运行或已经通过 |
| deploying | waiting_external（deployment） | 等独立部署执行器的真实结果 |
| awaiting_deployment | waiting_external（deployment） | 同上，部署阶段不作为任务业务状态 |
| continued | cancelled | 旧实现已把后续工作交给另一任务；原记录停止，不推断完成或复制续做任务 |
| completed／failed／cancelled／needs_attention | 保持原状态 | 已完成和用户停止的工作不自动重建 |
| 未识别状态 | needs_attention | 保留事实，等待明确处理 |

任务迁移保留 SQLite backup API（包含 WAL 中已提交页）的独立备份和原子版本键 `operation_task_states_v2`。在 Application 打开业务库前增加整库升级：SQL、逻辑重建和备份恢复归 `persistence/upgrades.py`，设置、污染、提示词及核对规则归 `services/upgrades.py`。旧设置映射到独立历史预算，未知键和值先存 `upgrade_archive` 后移除，其他旧值不变，新字段补默认。删除的旧 `context_prefix` 同样归档；旧迁移日志及尚未证明已完整归属外部库的表保留，不参与新运行查询。任务旧 delivery 列迁入 task_delivery，由同一仓储关联返回。

升级完成标识为 `continuous_history_upgrade_v1`。已完成的启动只检查该记录、设置键、结构标记、旧 delivery／compose 和提示词表，不整表加载消息／人物／记忆／任务／回执，也不做全库 integrity_check。缺少后续新增的设置默认值由 StateRepository 补齐；未知或旧名设置在事务内归档并清理，不产生新的整库备份。污染修正仅在首次完成该升级前执行；以后即使需要修复结构也不重跑污染修正。新建库初始化后直接记录当前完成标识。升级完成后的完整内容摘要与全库校验由离线预检承担。

旧工具上下文压缩检查点的失效由同一升级入口执行：先整库备份，将受影响检查点存入 `upgrade_archive`，再删除旧投影并记录完成标志。历史原文和工具配对保留，之后从原始记录重建。已有精简标志的数据库不重复失效；仓储初始化不执行这项清理。

损坏的 prompt_versions 不尝试只做 REINDEX 或直接 DROP：先备份，再逻辑复制其余完整表，重建提示词表与 FTS 投影，仅保留字段类型及键结构可识别的提示词。异常记录只在备份，报告列数量、ID 和摘要。全部迁移后 integrity_check 必须为 ok；任一步失败关闭连接并恢复本次整库备份，不启动执行器或补发通知。离线命令 `tools/upgrade_preflight.py` 核对五类原记录身份和内容摘要，并实际查询近期互动、角色历史、任务、回执和记忆，事务内试续做后回滚。重复预检验证文件哈希不变。2026-11-15 已在生产一致快照副本完成离线迁移与迁移中途失败恢复；实际停服、部署和平台验收尚未执行，步骤见 [上线](upgrade.md)。

启动恢复不启动未知副作用：未开始的尝试／排队任务回到 queued；未闭合工具调用进入 reconciling；无法判断的在途尝试结束为 interrupted，任务进入 needs_attention；业务 cancelled 保持不变。retry_wait 保留原 deadline，waiting_user 保留待决问题。停止请求也持久保存，进程重启不会自动恢复用户已停止的工作。

### 单步错误与重试

`services/task_errors.py` 是纯函数，接收异常类型／状态码或明确的错误类别，不把日志文字当成执行成功证据。

| 错误类别 | 下一业务状态 |
| --- | --- |
| 网络、连接超时、限流、可恢复服务端错误 | retry_wait；预算耗尽后 needs_attention |
| 参数无效、工具不存在 | needs_attention，修正接口或参数后人工续做，不原样循环 |
| 写入结果未知 | reconciling，保留原操作参数与记录，先核对 |
| 权限拒绝 | waiting_user；不自动重试绕过权限 |
| 输出格式错误／空输出 | retry_wait，仅重做未成功的模型请求；预算耗尽后 needs_attention |
| 长命令仍运行 | waiting_external；保留返回的句柄／事实，不重新提交命令 |
| 发送结果不明 | reconciling（执行错误分类）；通知回执独立保留 sending／unknown，不重发 |
| 持续不可用／无法归类 | needs_attention |

后台 `task_retry_limit` 默认 3，可设 0–3，含义为初次请求之后最多 3 次自动重试。每次成功的安全步骤重置该步骤预算；下次执行时间持久化，退避为 2／4／8 秒。调度器每秒检查到期项，再排队创建新尝试；retry_wait 没有占用执行槽的协程，也不重新执行检查点之前已完成的工具。最多 3 个后台执行槽，最多 12 项活跃代理任务；开发任务仍只允许一项持有工作区。无整项任务墙钟截止时间。

核对基线为已安装 AstrBot 4.29.4 及该测试环境 SDK 源码：

| 层 | 原有次数 | 后台任务处理 |
| --- | --- | --- |
| 石英旧 run_agent | 共 3 次尝试，槽内 sleep | 删除；由持久调度器控制单步预算 |
| 宿主 runner | 空输出共 3 次尝试，另可切换 fallback providers | 任务 runner 单次请求，不走该重试／fallback 包装；保持 full 工具模式，无 skills_like 二次取参 |
| 宿主 request_retry | 默认共 5 次请求 | `request_max_retries=1`，含义是共一次请求，不是额外一次 |
| OpenAI／Responses 提供者 | SDK max_retries=0；提供者外层最多 10 轮错误修复／换 Key | 每个任务使用提供者副本，错误直接上交，不换 Key 原地循环 |
| Anthropic SDK | 默认额外重试 2 次，宿主没有覆盖 | 副本 client.with_options(max_retries=0)，不修改前台共享实例 |
| Gemini 提供者／SDK | 外层最多 10 轮，查询内有格式修复循环；非流式 recitation 额外 2 次；SDK 未配 retry_options 时通常一次，另有隐式流重试分支 | 副本禁止外层循环；每次模型调用只允许一次 query config 准备；每请求显式 SDK attempts=1，防止内层修复及隐式重试相乘 |

真实宿主测试使用脚本模型和假传输验证次数、空输出预算以及已完成写工具不重跑；第三方提供者自身隐藏的重试和真实服务端行为不属于这组已验证范围，接入前需核对。前台聊天和统一表达服务仍沿用各自原有策略。

取消先持久记录 cancelling，再请求执行端停止；确认结束且没有未知工具结果时 cancelled。工具回执未闭合、独立外部执行无法确认、或 5 秒内未收到停止确认时进入 reconciling，保留现场。执行端尚未停止时拒绝 resume；迟到结果不能把被停止的任务标成完成。

### 部署链与接口

独立部署目录中的 queued／running／issued／completed／rolled_back／failed／unknown 是部署执行器状态，不迁入任务状态列。开发任务提交部署后为 waiting_external，wait_reason=deployment；收到完成证据才进入 completed，失败或不明转 needs_attention。收到结果后经同一 transition 入口归并，已停止的任务不复活；部署通知仍独立按真实回执去重，不因业务状态变更重新发送。

`/api/v1/operations/tasks`、详情、cancel、resume、redeliver 路径保持兼容。resume 可带 `{"answer":"原用户答复"}`，保留任务 ID；详情增加 attempts、next_run、retry_count。问题与后续结果使用各自稳定通知标识，避免同一任务的问题回执吞掉最终结果。前端 TaskStatus 使用新状态联合类型，开发任务“完成”和独立部署“完成”分别展示。


## 持续授权与通知发件箱

授权记录与策略规则分别位于 persistence/authorizations.py、services/authorizations.py。授予者、原输入引用、管理员、设备、提供者、原会话、任务／执行会话、类别、有效期、版本和撤销审计均为持久数据。后台或模型不能用工具输出创建授权；聊天授权须匹配明确范围的原话，WebUI 操作须匹配已鉴权收件箱保存的表单。设备访问权经 computer.control devices 单独复核，策略不授予访问权。adapters/authorizations.py 只调用现有能力；原生电脑批准协议不进入核心。

确认事件和输入引用原子保存，审批操作标识在任何批准调用之前预占。重复与未知只查询原 request_id；只有完成回执精确对应原执行会话及批准对象才记 confirmed。等待授权的问题通过统一通知入口按原会话合并；重启补交尚未送出的提问。A01–A03 的本地实现、审计及限制见 plugin-protocol.md。已用本机独立电脑插件的真实 main.py／transport.py 加模拟 WebSocket 设备验证持久幂等、首次及重连 validate、撤销阻断排队命令与真实回执形状；真实 Windows 客户端及真实平台尚未运行验收。客户端过期 allow 降级和 method 丢失的处理边界见 plugin-protocol.md。

通知业务记录在 notification_outbox，事实所有权在 notification_fact_claims，迁移期发送所有权在 notification_send_owners / notification_event_owners，平台投递状态仍在 notification_receipts。它们不改变 operation_tasks.status 或 task_attempts.status。input_events 保存通知的持久接收位置并引用 messages 原事实；outbox 的初始 facts 不重复保存正文，只在合并／过滤时保存派生事实。

| 发件箱状态 | 含义与恢复 |
| --- | --- |
| pending / merging | 排队或等待合并；重启继续，原会话新输入优先 |
| delivering | 选择、表达或发送中；重启先读底层回执，不能直接重发 |
| suppressed | 安静事件、已有回报、事实过时或兼容发送者所有；事实与依据可查 |
| sent | 底层 platform_accepted；聊天与核心历史以同一回执幂等写入 |
| unknown | sending 残留或发送调用未确认；不写已发送历史，不自动重发 |
| failed | 确认未开始发送的表达／运输准备失败；原范围 retry 可重新排队 |
| cancelled | 原提交者在表达开始前撤回；终态，submit／retry 不复活 |

底层 deferred 表示表达期间来了新输入或事实发生变化，未开始平台发送，允许重新排队。原 failed/interrupted/composing 的明确补发行为保留。进展回执不会覆盖任务最终结果的 delivery 投影；部署执行器结局保留在 deployment_status，业务状态取任务表，两者不混用。

`message.notify retry/cancel` 的规则位于 `NotificationOutbox.operate`，状态比较写入位于 `OutboxRepository.move`。retry 只领取确认未发出的 failed 和无活跃执行者的 interrupted／composing；cancel 只接受 pending／merging 且没有表达回执，分类等待期间取消后也不能被进展合并复活。两者校验原会话／原提交者及消息类型，返回当前状态和 applied。已发送、未知、静默、抑制及正在表达的项拒绝重新排队，模型工具仍不能直接转发可信通知能力。

`notification_outbox.fallback_text` 通过加列迁移，默认空字符串，与新记录使用同一查询。submit 的插件可读短句最长 1000 字符，校验只豁免“原样包含 facts 中 80 字以上字符串”这一项；裸 JSON、提示词结构、堆栈、人格原行和长度仍检查，拒收兜底不拒收通知。表达服务只从当前领取的通知获取已校验文本，不从 facts／事件 body／异常推导；必要结果表达失败或成功表达因原样引用长事实被拦时使用兜底，进展不用。后台表达本身仍严格检查，没有兜底时行为不变，运输函数及发送前 preflight 保持原实现。必要结果让路最多 `notification_max_delay`（默认 60 秒），进展不享受该上限，紧急优先级不变。

统一路径为：核心原 send_once 调用或 message.notify 提交 → 原子接收／所有权 → 通知价值选择 → 同事实去重／进展或确认问题合并 → 原会话表达 → 再检查新输入、事实和原始资料泄漏 → 原 Notifications.send_once 运输 → 回执及历史。规则确定的安静／关键事件不调分类模型，普通进展复用已选决策后端及其时延预算；失败静默。选择结果写入 decisions 与通知记录。停止、撤权、需要决定的阻碍有独立高优先级通道，不排在普通后台表达后。任何队列写入不持有宿主会话锁。

已收敛任务结果、ask_user 提问、前台等待超时及最终超时说明、部署结果、停止确认、持续授权提问。删除这些入口直接承担发送时序的职责，保留现有统一运输代码，没有增加 event.send / send_message 调用点。普通聊天按已定设计继续走宿主 agent 阶段；包含任务事实的前台回复在原发送调用前持久预占，成功才确认，发送未知也阻止后台重报同一事实。普通无任务聊天不额外存通知记录。第二气泡、表情仍在会话锁外，文件导出保留原附件发送，不纳入文本通知队列。独立电脑插件的结果、错误、断线及监工通知已转入 message.notify；仅目录没有该能力时使用安全的 compose 兼容入口，旧发送回执不重提，每个新事件持久固定发送所有者。2026-11-15：独立提醒也接入 submit/status/retry/cancel 和内容兜底，真实插件联调见 `tests/test_reminder_plugin_integration.py`；业务与重试时间表仍归插件，未尝试旧投递首次处理再定所有者，已尝试兼容投递保持原路径。未验证真实 QQ、真实模型或线上迁移。

AstrBot 4.29.4 的 aiocqhttp send 会等待底层 OneBot 发送调用并在异常时上抛；正常返回 None，宿主主动 send_message 返回是否找到平台并等待 send_by_session。核心沿用该宿主确认边界，False、异常和超时均不当作送达。它不是用户已读证明；真实 QQ／其他平台的服务端回执以及发送未知的人工核对尚未联调。真实 runner 测试使用脚本模型与假平台，只证明核心排队、原会话与去重时序。

授权页与通知页分别使用 /api/v1/authorizations、/authorizations/action、/notifications；原任务 redeliver 路径保持兼容。所有接口沿用现有管理员认证和输入收件箱，没有新增未鉴权端点。
