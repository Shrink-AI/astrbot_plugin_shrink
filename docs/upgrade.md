# 数据库升级与回滚

日期：2026-11-15。适用于接近 `3f9112e`、具有旧 messages／digests／operation_tasks 结构的核心库。线上版本含独有修改，不能只用提交号认定兼容。操作前须先在一致副本上完成预检。

## 升级前准备

1. 保存当前插件源码与版本、独立插件源码、宿主配置、提示词目录及覆盖历史、工作台、知识库与关联、未完成任务和独立部署执行器记录。确认恢复权限与磁盘空间；数据库备份不足以恢复外部知识库或已被更新的源码。
2. 记录宿主插件启用范围、前台与后台 provider、请求尝试、空输出预算、fallback、工具超时和 main_enable 的持久值。待确认项见下表，本工具不修改宿主配置。
3. 准备 Python 环境及核心依赖，在隔离副本先运行本页命令。迁移入口不导入 AstrBot，不联网、不调用模型、不启动任务执行器。
4. 停止宿主及所有会写目标库的进程，包括独立重载／部署执行器；确认没有残留写入者。为正式数据库、WAL、SHM 做停服成套存档。不要把运行中的 `.db` 单文件复制当作一致备份；在线取一致副本必须使用 SQLite backup API。
5. 独立提醒与电脑库分别成套备份。核心不读取、迁移或接管其业务表。核心遗留提醒表暂保留，不能因独立插件有同名表就删除。

以下命令中的相对路径均在核心仓库执行，`runtime/upgrade/shrink.db` 必须是待验证的停服副本。报告、备份和库含敏感资料，不能提交或公开分发。

```powershell
.venv/Scripts/python tools/upgrade_preflight.py runtime/upgrade/shrink.db --report runtime/upgrade/first.json
.venv/Scripts/python tools/upgrade_preflight.py runtime/upgrade/shrink.db --report runtime/upgrade/repeated.json
```

先建立目标目录并放入一致副本；报告父目录须已存在。两个命令退出码均应为 0，首次为 `ok`，重复为 `unchanged`。失败时不要启动服务。

## 预检内容与通过条件

工具先只读扫描，再通过 SQLite backup API 建立唯一的 `*.before-upgrade-*.db`，备份成功后才修改目标。备份可能保留已知损坏，这正是事故现场；它的文件哈希与导出文件因 SQLite 页头变化可能不同，不能由此认定业务内容发生变化。

- prompt_versions：逻辑复制完整表到新库，不在损坏 btree 上直接 DROP，不只做 REINDEX。提示词记录要求 ID、键形态、正文、说明和时间类型可识别；异常 ID、数量和内容摘要写报告，异常原文只留备份。FTS 从原内容重建。
- settings：旧 context_compress_tokens／context_retain_ratio 映射为 history_compress_tokens／history_retain_ratio；其他旧值保留，新字段补默认。未知键和值先存 upgrade_archive 再从当前设置移除。Settings 仍拒绝未知字段；已完成升级的启动只清理设置，不重复整库备份或污染修正，后续新默认值由设置仓储补齐。
- 结构：补新表与列，任务 delivery 从旧业务列迁入 task_delivery，调用方仍从同一 Tasks 查询获取。13 个旧 context_prefix 锚点归档后删除，新角色历史不读取旧锚点。旧 migrations 日志及未证明已完整归属外部库的遗留表保留，不为旧记录另设字段或过滤。
- 数据：消息、人物、记忆、任务、通知回执逐身份核对原字段内容摘要；只允许报告列出的污染修正及状态机映射。近期互动、会话重建、记忆查找／FTS／召回、任务状态和回执用新代码实际查询。对待续做任务执行状态服务 resume 探测后事务回滚，不执行任务或工具。
- 历史：旧 messages 建角色日志、旧 digests 建带原文引用的检查点；已有检查点幂等补齐摘要状态、尝试次数和窗口字段。128000 估算 token 阈值内完整历史不会被旧摘要遮掉；越界先固定边界，摘要由后台补做，失败不阻塞前台。估算计入角色／工具元数据，不能替代提供者准确 token 计数，也不承诺缓存命中。
- 污染：只自动修剪具有至少两种明确提示词标记、且现有清理器能提取安全正文的机器人草稿尾段；用户引用不动。裸 JSON、堆栈、思考标签与模糊单标记单独计数；没有明确派生证据的记忆／表达／摘要保留。无审核队列或运行期污染过滤。
- 结尾：全库 integrity_check 必须为 ok，所有原记录摘要一致；重复执行数据库文件哈希不变。失败关闭连接后恢复本次备份，报告为 failed_restored；failed_restore 表示恢复未完成，必须手动处理，不能启动。failed 表示还未建立可恢复迁移现场，不代表已回滚。


## 启动与健康检查

1. 人工核对报告中的修正、保留表与待决定项。在宿主仍停止、无写入者时安装与迁移匹配的新源码，将通过预检的数据库放到正式核心数据目录。不要让旧库的 WAL／SHM 与替换后的新库混用；旧文件先完整移入停服备份位置。
2. 按分别确认的版本更新独立提醒插件。它的首次 owner 迁移仅将已尝试投递归兼容路径；未尝试记录在首次投递时固定所有者。不要运行旧版“修复未发布中间态”的 SQL。
3. 启动宿主一次，观察核心迁移是否幂等成功、各插件是否加载。Application 会在打开业务仓储前调用同一升级规则；不要用自动启动替代离线预检。个人 `tools/update.py` 不包含完整离线预检流程，不能直接以其“备份后启动”当作本页验收。
4. 在已鉴权后台检查新历史设置为 128000／0.65，其他旧设置未变；查看人格与 contract 生效版本、旧 compose 历史和迁移归档。
5. 查看任务总数、原会话、创建者、状态、通知回执和历史。10 项 needs_attention 保持；1 项原 interrupted 因未闭合工具进入 reconciling。先核对副作用证据，再决定是否恢复，不能批量重跑或自动补发。
6. 在指定隔离测试会话验证连续两轮角色历史、工具轨迹与前缀比较，确认模型当前请求工具集中没有 transfer_to_*，后台分配工具仍可用。检查近期互动与记忆召回的身份范围。
7. 经另行授权后，用测试提醒验证完整长内容一次发送、失败／未知不盲目重发；查看真实平台接受回执。测量 turn_traces 的 p50／p95 与最长等待。离线脚本模型测试不能代替这些步骤。

## 失败回滚

1. 停止宿主及独立执行器，保留失败报告、失败现场库及 WAL／SHM；不要覆盖最后一份旧源码和停服备份。
2. 工具失败且报告 failed_restored 时，先核对目标文件哈希等于报告 backup_sha256；它恢复到迁移前状态，包括原有损坏，不能视为新版本可用。
3. 如启动后验收失败，成套恢复旧源码、旧数据库及与它配套的配置／提示词／工作台／知识库关联。关闭所有连接后替换数据库，不混用不同代次的 WAL／SHM。独立插件若也升级，分别恢复对应源码和库。
4. 使用旧版本重新启动，再核对任务与回执。迁移后运行期间新增的数据应先保存现场，不能无声覆盖；这段增量需要单独回收，迁移备份不能自动合并上线后的业务增量。

## 提示词迁移与逐键清理

不修改 chat.persona 默认和覆盖，不新增接梗、追问、亲近、空格断句或禁口头禅规则；普通群友、少点评少吐槽、长短不一、句末不加句号等既有口吻保持。

| 默认键 | 调整及理由 |
| --- | --- |
| history.compress | 单层变量改为双层，真实模板填入待压缩历史；max_tokens 指定摘要正文容量 |
| chat.turn.current | 删除不存在的“标了当前”标识引用，沿用本轮发言人与触发原因 |
| tasks.coordinator | 修正说明文字，不再暗示前台超时会自动创建代理；正文路由语义不扩展 |
| tasks.agent_policy | 不再要求仅任务结束时回报；允许既有 ask_user 与实质阻碍交还，内部步骤安静 |
| tasks.orchestrate.workflow | 删除程序已实施的身份继承／原会话原创建者校验重复说明，保留原任务选择与已接收含义 |
| tasks.orchestrate.limits | 删除写死并发 3／重试 3 的提示词副本，按实际后台设置与状态；保留 retry_wait 不占执行槽 |
| tasks.workbench_guide | check 说明包含实际分层／发送检查；“一次请求只通知一次”改为同一事实不重复回报，避免问题回执吞掉最终结果 |
| outbound.contract | 受理一句极简短句、不复述参数／路径／模型／步骤、不介绍同构体或派工过程、不加等待／回报尾巴，重复受理安静；提到子代理叫“我的同构体”，不把尚未派出的任务说成已交出去。结果／失败／未知／待决定事项照常保留 |

四处线上定制的处理：

- chat.persona 覆盖逐字保留，迁移前后内容 SHA-256 相同。
- outbound.compose 的旧完整覆盖保留历史；规则拆成 outbound.contract 覆盖，当前人格段及熟人聊天段替换对应默认段，其余逐句去重保留，旧派工说明按新契约取舍。compose 新版本重置为只含资料的默认。后台可查看旧全文并恢复；恢复旧全文会重新引入重复规则，应先评估。
- chat.acceptance_policy／outbound.acceptance_policy 不恢复加载或自动追加。工具前提示及其依赖内容退役，短受理和必要信息保留并入默认契约；若数据库曾存过目录外键，则保留为可查历史而不生效。
- 2026-11-15 用户已决定仅约束受理一句：不介绍同构体或派工过程、不加等待／回报尾巴；“同构体”称呼仍是人格设定，提到子代理时仍叫“我的同构体”。默认契约与线上人格覆盖的受理口径一致，无须编辑人格覆盖；失败、未知、需要决定的事和最终结果照常如实说明。迁移保留两段用户定制，契约末两行使用这一口径。
